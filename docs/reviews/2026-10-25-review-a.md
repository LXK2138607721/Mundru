## P1：已接受的撤销随 Activity 销毁丢失

### 定位

- `D:\test\Lumina\app\src\main\java\com\lumina\cleaner\MainActivity.kt:134`：写队列绑定 `lifecycleScope`。
- `D:\test\Lumina\app\src\main\java\com\lumina\cleaner\core\database\PhotoWriteQueue.kt:18–20`：每个已提交操作是该 scope 的普通子任务，并先等待前一任务完成。
- `D:\test\Lumina\app\src\main\java\com\lumina\cleaner\MainActivity.kt:1135–1143`：右滑先更新 UI，再把恢复事务排入队列。
- `D:\test\Lumina\app\src\main\java\com\lumina\cleaner\MainActivity.kt:1152–1163`：暂存事务完成后，队列任务仍须等待统计读取。

### 条件与调用链

1. 上滑暂存 A，Room 暂存事务已经完成。
2. 暂存任务随后的 `getTotalReviewedCount()` 尚未结束（或其他前序写入仍在等待数据库）。
3. 用户右滑撤销；UI 已返回 A，但恢复事务仍在队列等待。
4. 此时旋转屏幕导致 Activity 重建，或结束该 Activity。Manifest 未自行接管配置变更。`lifecycleScope` 在生命周期销毁时取消其子任务，队列中的撤销不会重新提交给新 Activity。

结果：A 仍在回收站，已经呈现为成功的撤销没有保存；同类窗口也会丢失尚未提交的保留/冷却更新。生命周期取消规则见 [Android 官方 LifecycleScope 说明](https://developer.android.com/topic/libraries/architecture/views/coroutines-views#lifecyclescope)。

### 非真机最小复现

- 源码：`D:\test\Lumina\app\build\review-a\LifecycleProbe.kt`
- 运行脚本：`D:\test\Lumina\app\build\review-a\run-probe.ps1`
- 编译输出：`D:\test\Lumina\app\build\review-a\probe-compile.log`
- 结果：`D:\test\Lumina\app\build\review-a\probe-result.txt`

探针直接编译当前生产 `PhotoWriteQueue.kt`，使用实际 coroutines 1.9.0 和 `Dispatchers.IO`；以可取消存储替身模拟“暂存已提交、统计读取悬挂、撤销排队”，取消 owner 后输出：

```text
ownerDestroyed=true uiIndex=0 persistedTrashed=true undoRan=false
```

这是队列取消语义的 JVM 复现；未启动 Android、未使用真实 Room 文件，不代表一次设备实测。

### 最小修复方向

由数据库/应用级 owner 接管已经接受的有限数据库写入，使用 Application 数据库而非 Activity 引用；UI 统计和完成反馈留在可取消的 UI scope。使新 Activity 的初始化同步和下一批读取观察同一写队列；不能仅把 owner 延长而保留 `MainActivity.kt:615–639` 的旧快照→`REPLACE` 并发覆盖窗口。补充“调用方销毁后已接受撤销仍完成”和“重建后的首次读取看到该撤销”的回归。
